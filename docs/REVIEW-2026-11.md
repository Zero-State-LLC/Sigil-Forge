## 1. What Sigil-Forge is, and where it stands

Sigil-Forge is a standalone Hermes skill, version 0.13.1: about 12,400 lines of
stdlib-only Python under `scripts/` behind one CLI (`scripts/sigil_forge.py`).
It turns a written intent into a deterministic glyph (Spare monogram, kamea
path, bind runes, rose cross, planetary seal), composites it into a wallpaper
PNG, and hides an intent digest, a commitment and optionally an AES-256-GCM
sealed "vault" in the image's low bits (SF12 format). It also writes run
receipts, a PROPOSED-only learning ledger, and an optional proof of intent
(local capsule, or Noir/RISC0 if those tools exist). It installs to
`~/.hermes/skills/sigil-forge` through `install.sh`, which stages, checks and
swaps the tree with backup and rollback (`scripts/install_transaction.py`).
There is no network code in the skill; the only subprocesses are `git`,
`resvg`, `nargo`, the staged self-checks and an operator-supplied background
command.

State: the code is careful in most places (authenticated encryption with a
constant-time tag check, `shell=False`, staged atomic run directories, a
session-id allowlist, refusal lists for harm and authority seals) and has 276
tests. The weak part was everything around the code. CI ran no tests, a
production deploy workflow for a different product sat in `.github/workflows`,
the documented stdlib-only install failed on a Python without PyYAML, and the
licence says three different things in three places. The repository is
**public**, and so is the archived personal copy
(`scrimshawlife-ctrl/Sigil-Forge`, MIT, archived, last push 2026-09-23).

## 6. Fitting Sigil-Forge into the Abraxas stack

Read for this section: `~/Abraxas/AGENTS.md`, `~/Abraxas/README.md`,
`docs/SIBLING_REPOS.md` and `.abraxas/subsystems/hyperlex_instrument_v1.yaml`.
Abraxas was not edited.

Abraxas's contract is: additive patches only, deterministic behaviour, shadow
and forecast lanes kept apart, derivative surfaces never confer authority,
every non-trivial subsystem registered in
`.abraxas/registries/expected_subsystems.yaml` with a metadata file, and no
readiness claim without receipts. It already has a worked pattern for an
external engine that must not influence forecasts: **Hyperlex**, a sibling repo
consumed through `abraxas.evidence.hyperlex_instrument`, lane `shadow`, flag
`ABX_HYPERLEX_INSTRUMENT` default off. Sigil-Forge should follow that pattern
exactly. It is an expressive artefact generator with an explicit "no efficacy
claims" rule, so it can never be more than an observation in Abraxas.

Recommended shape:

1. **Stay a sibling repo, not vendored code.** Abraxas is MIT; Sigil-Forge is
   currently proprietary. Until rank 1 is settled, Abraxas should call an
   installed Sigil-Forge and hold only an adapter.
2. **Subsystem record** `sigil_forge_instrument_v0` (new file under
   `.abraxas/subsystems/`, added to the registry): `lane: shadow`,
   `canon_status: shadow_advisory`, `allowed_change_classes: [additive_patch]`,
   `required_receipts: [sigil_forge_instrument_unit]`, revocation triggers
   `shadow_leakage_into_forecast` and `treat_sigil_as_evidence_of_outcome`.
3. **Adapter** `abraxas/evidence/sigil_forge_instrument.py` behind
   `ABX_SIGIL_FORGE_INSTRUMENT` (default off), roles limited to `OBSERVATION`
   and `SHADOW_SIGNAL`, `influence_policy=NONE`, `valid_for_forecast=false`.
4. **Only public surfaces cross the boundary.** The adapter reads
   `artifact-root.json`, `run-receipt.json` and the SF12 public header
   (`intent_digest`, `sigil_root`). Plaintext intent, the commitment nonce, the
   passphrase and the capsule never enter Abraxas ledgers. This matches
   Sigil-Forge's own invariant and gives Abraxas a hash it can link without
   holding anything private.
5. **Determinism gap to close first.** Abraxas requires deterministic,
   replayable runs. Sigil-Forge's glyph geometry is deterministic in the intent
   digest, but each run draws a fresh commitment nonce, salt and GCM nonce from
   `os.urandom` and stamps a wall-clock run id. The adapter must hash only the
   deterministic fields (`intent_digest`, `sigil_root`, method ids, skill
   version) and record the rest as non-replayable, or Sigil-Forge needs an
   explicit replay mode that takes nonce and timestamp as inputs. I recommend
   the first; a replay mode invites nonce reuse.
6. **Name collision.** Abraxas already has `server/abraxas/pipelines/sigil-forge.ts`
   (module `abraxas/pipelines/sigil-forge`, registered as `mod-sigil-forge-001`)
   and a `SigilGenerator` UI component. That is a different, TypeScript
   "ritual sigil" pipeline. Decide whether it is retired, renamed, or becomes a
   projection of this engine's output; until then the new subsystem id must not
   reuse the bare name.
7. **Proof targets for the first drop**, in Abraxas's envelope terms: a unit
   receipt showing the adapter refuses to run with the flag off; a receipt
   showing no forecast-lane module imports it; a golden test that the same
   intent yields the same `intent_digest` and `sigil_root` across runs; and an
